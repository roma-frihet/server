# readOnly 트랜잭션 안에서 한 쓰기가 조용히 사라짐

- 요약: `ReportService`는 클래스에 `@Transactional(readOnly = true)`가 걸려 있는데, 그 안에서 `ClassroomRecordsReader.read()`가 `AttemptFinalizer.finalizeExpired()`를 불러 시간이 지난 응답을 확정한다. 확정은 더티 체킹에 의존하는 쓰기다. `readOnly = true`면 Hibernate가 세션을 `FlushMode.MANUAL` + `defaultReadOnly`로 두어 변경이 플러시되지 않는다. 그래서 교사가 대시보드, 학생 목록, 학생 상세를 열어도 응답이 확정되지 않았다. `findScores`는 아예 확정을 부르지도 않았다. 결과적으로 학생이 문제를 열어 두고 돌아오지 않으면 그 문제는 영원히 미확정으로 남고 교사 화면의 점수가 실제보다 낮게 나왔다. 코드 리뷰 중 발견했다.
- 원인: 같은 실수를 `StudentPasswordResetService`에서 한 번 겪고도 패턴으로 일반화하지 못했다. 그때는 "외부 호출이 트랜잭션에 들어간다"는 쪽에 주목해 `readOnly`가 쓰기를 삼킨다는 절반을 기억에 남기지 않았다. `AttemptFinalizer`는 MockK 단위 테스트만 있어서 영속성 경계를 전혀 건드리지 않았고, 통합 테스트는 모두 학생 경로(`AttemptService`, `StudentReportService`)만 확인했다. 둘 다 쓰기 트랜잭션이라 통과했다. "읽기 메서드가 사실은 쓰기"라는 구조를 테스트가 비춘 적이 없었다.
- 재발 방지: 확정을 부르는 `findStudents`, `findStudentDetail`, `findDashboard`, `findScores`에 `@Transactional`을 붙여 쓰기 트랜잭션으로 만들고, `findScores`에는 빠져 있던 확정 호출을 `ClassroomRecordsReader.finalizeExpired(courseId)`로 추가했다. 교사 경로 3개를 실제 DB로 확인하는 `TeacherReportFinalizationTest`를 추가했다 — 고치기 전에는 3개 모두 실패하고 고친 뒤 통과하는 것을 확인했다. 앞으로 더티 체킹에 기대는 코드를 부르는 메서드는 호출 사슬 전체의 `readOnly`를 확인한다.
- 강제 수단: 문서와 테스트. 같은 실수가 한 번 더 나오면 ArchUnit으로 올린다 — 더티 체킹으로 상태를 바꾸는 컴포넌트(`AttemptFinalizer` 등)를 주입받는 Service는 클래스 레벨 `readOnly = true`만으로 끝내지 못하게 막는 방식이 가능하다.
